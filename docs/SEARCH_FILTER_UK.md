# Search / Filter — 2.8.0

Пошук каталогу є server-first і не залежить від JavaScript. Базовий SQL-пошук працює за назвою, коротким описом, SKU, GTIN, MPN, брендом і текстовими характеристиками. Додатковий шар синонімів не є критичною залежністю: якщо таблиця синонімів недоступна, запит виконується за вихідними словами.

## Синоніми

Групи зберігаються окремо для `store_id` і locale. Одне слово пошукового запиту може бути розширене альтернативами з тієї самої групи. Різні слова запиту залишаються обов'язковими: між токенами використовується AND, між синонімами одного токена — OR. Кількість токенів і альтернатив обмежена, щоб довільна конфігурація не створювала неконтрольований SQL.

Керування: `Каталог → Пошук`. Група повинна містити 2–20 різних значень. Видалення групи не впливає на базовий пошук.

## Фасети характеристик

У фасети потрапляють тільки definitions із `filterable=1`. Підтримуються boolean/bool, decimal/number та text. Значення передаються у URL як непрямі валідовані токени. Для тексту використовується SHA-256 hash, тому довільний текст характеристики не вставляється у SQL або URL як SQL-умова.

Кілька вибраних значень одного атрибута об'єднуються через OR. Різні атрибути — через AND. Одночасно дозволено не більше 12 атрибутів і 12 значень одного атрибута.

## SEO

Звичайні пошукові та фасетні query URL мають `noindex,follow`. Індексовані SEO landing filters повинні бути окремою керованою сутністю з власним canonical/slug; runtime-фасети навмисно не перетворюються на індексовані сторінки автоматично.

## Відмовостійкість

Синоніми — optional relevance layer. Їх збій не повинен викликати 500 на каталозі. Сам catalog/filter залишається SSR-first і працює без JavaScript. Некоректні `attr[...]` параметри відкидаються whitelist-валідацією до створення `ProductCatalogFilter`.
